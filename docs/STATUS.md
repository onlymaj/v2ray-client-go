# Project status

Last updated: 2026-10-13

## Done

- All eight spec milestones are implemented except the items under "Not done yet": protocols (VLESS + Vision, VMess AEAD), transports (TCP, uTLS, Reality, WebSocket, gRPC), inbounds, DNS forwarder, health checks, stats, groups, rules, RouterOS sync, kill switch, API, UI, RouterOS guide, Dockerfile.
- Image: 2.56 MiB (limit 8 MB). Binary 9.2 MiB raw, 2.5 MiB after UPX. UI 107 KB gzipped (limit 150 KB).
- Checked on this machine only, in a network namespace: REDIRECT installs through nftables and through legacy iptables, all listeners come up, login, import, security headers and connection caps work.
- VLESS was tested against a real Xray v26.3.27 server: Reality + Vision (chrome, firefox, safari), TLS + Vision, TLS without flow. 10 of 10 scenarios passed.
- Security review: twenty-one rounds of reviewers, about 265 findings, all fixed with regression tests except the ones listed under "Known limits".
- Stress test (round 7): the `-race` build ran in three network namespaces (LAN clients, the app, a real Xray server with VLESS TCP, VMess TCP, VLESS WS, VMess gRPC+TLS and VLESS TLS+Vision) for 75 s under SOCKS, HTTP CONNECT, transparent, TLS-sniffed and DNS traffic with config changes and SSE logouts at the same time. No races, panics, corrupted transfers, deadlocks or leaks. Repeated after the round-8 fixes (45 s) and the round-9, round-10, round-11, round-12 and round-13 fixes (30 s each) with the same result. Not yet repeated after the fixes of rounds 14 to 17, which change the gRPC data path.

## Known limits, accepted on purpose

- A login flood can block admin devices that have never logged in, until it stops. Up to 16 devices that logged in before stay exempt.
- Sessions are tied to the client IP. If the admin device's IP changes, it must log in again.
- The RouterOS certificate is verified only when `certSha256` is set.
- `allowInsecure` can still be turned on by hand in the client form. It shows a red badge.
- Clients with no transport encryption are allowed and show a red "unencrypted" badge.
- UDP other than DNS is not proxied. The kill switch and the routing rules cover IPv4 TCP only; `docs/routeros.md` makes disabling or blocking IPv6 a required step.
- A LAN device that sends a forged TLS SNI or HTTP Host matching a `direct` domain rule gets a direct connection to whatever IP it dialed. Direct connections keep the original destination address on purpose; the sniffed name only selects the rule. Reported in round 8, not changed.
- A LAN device with four or more source addresses can hold all 64 UI connection slots and keep admins out until it stops (same class as the login flood above). Reported in round 8, not changed.
- A LAN device that forges many UDP source addresses can fill the DNS handler slots, each source staying within its own limits, and slow name resolution for everyone while it keeps sending. Sources that hold more than their fair share of upstream slots are refused first (round 10), but forged sources cannot be told apart. Reported in round 10, not changed.
- Port changes in the settings (including setting SOCKS, HTTP or DNS to 0) take effect only after a container restart; the listeners are bound once at start. The UI and `web/API.md` say so. Rebinding at runtime was not added (round 11).
- A `dest` rule sees only the IP the device connected to. A proxied connection that carries a host name (sniffed, or given to SOCKS5 or HTTP CONNECT) goes to the proxy server by name, so a `dest` rule cannot block or redirect an address reached that way; a device can forge the name. Direct connections are checked after resolving. Documented in `web/API.md`. Closing it for sniffed names would mean sending the original IP instead of the name whenever a `dest` rule exists (Xray's `routeOnly`). Reported in round 12, not changed.
- Turning RouterOS sync off or renaming the address list leaves the app's entries in the old list. `docs/routeros.md` section 9 gives the command to remove them. Reported in round 12, not changed.
- The cap on slow gRPC streams charges the device with the most slow streams. A LAN device that uses 32 or more source addresses with one stalled stream each makes every source equal; the stream ended is then the oldest waiting one of any device, so it can have other devices' paused downloads cut (same class as the multi-address items above). Reported in round 16, not changed.
- Host names whose addresses change on every lookup (a hostile subscription, or a CDN-fronted server) make the app remove and add entries in the router's `no-proxy` list on every resolve, every 5 minutes: up to 2048 writes each way at the caps. The size of the list is bounded, the turnover is not. Reported in round 16; only the logging was reduced to one line per pass.
- A subscription URL whose host resolved to a public address when it was added and later resolves only to a private one makes "Refresh" send one GET to that LAN address (the path and port are in the URL; the reply is not shown beyond a clipped error). Names that resolve only to private addresses are allowed on purpose, for a subscription hosted on the LAN, and the app does not remember which kind a subscription was. Reported in round 16, not changed.
- Kernel socket buffers of the connections to proxy servers and direct destinations are left to the kernel (up to `tcp_rmem`/`tcp_wmem`, 6 and 4 MiB by default). A device that stops reading downloads, or a server that stops reading uploads, can have a few MiB queued per connection in kernel memory, outside `GOMEMLIMIT`; 64 connections per device are allowed. A fixed buffer would bound a download to about buffer / round-trip time (about 10 Mbit/s at 200 ms with the kernel's default `rmem_max`), so it was not set. Only the LAN-side sockets are bounded (round 18). Check on the router what `tcp_rmem`, `tcp_wmem` and `tcp_mem` are in the container and whether `memory-high` counts socket memory; if it matters there, set `SO_RCVBUF` in the dialers' `Control` or write smaller maxima to the container's `/proc/sys/net/ipv4`.
- A LAN device with four or more source addresses that keeps its newest connections in dials that hang (a direct route to an address that does not answer, 10 to 15 s each) can keep the 32 "evicted, still closing" places taken, and new connections from other devices are then refused while the table is full: an evicted connection's dial is not cancelled. Fixing it means passing a context from the inbound slot to `Handle`. Reported in round 18, not changed.
- Traffic and delay history is kept per client: 12 KB once it carried traffic and 5.8 KB once a check succeeded, released after 24 quiet hours. Measured after round 21: 18.2 KiB per client with both. At the cap of 250 clients that is up to 4.5 MiB (the cap was 1000 until then, 17.8 MiB). Reported in round 18, not changed; smaller rings (16-bit delays, 5-minute buckets) would be the fix.
- **Open decision.** uTLS v1.8.2 (the latest release) allocates the declared uncompressed size of a compressed certificate, up to 16 MiB, before checking it (`u_handshake_client.go`, `decompressCert`). The Chrome hello advertises certificate compression, and in TLS 1.3 the message comes before the server is authenticated, so a hostile proxy server, or anyone on the path of a `tls` client, can make every handshake allocate 16 MiB; a server with a valid certificate could also keep a padded certificate in memory for the life of the connection. Several handshakes at once exceed `GOMEMLIMIT` and can get the container killed. Not fixed: leaving the extension out of the hello removes the allocation but the hello then no longer matches Chrome's, which is what the fingerprint is for; limiting handshakes to a few at a time would slow every page load. The owner decides; it should also be reported to uTLS. Found in round 19.
- A `config.json` written by a build before round 17 can hold values that are refused now (more than 250 clients, which were allowed up to 1000 until round 22; a domain rule value such as `.example.com` or a list in one value, a group member listed twice); `Open` then fails and the container does not start. Only the settings are repaired on load. Nothing is deployed yet, so it was left; before the first release either keep the checks as they are or add a repair for rules and groups. Reported in rounds 17 and 19.
- With `ROS_URL` set, the RouterOS sync runs with that URL whatever `enabled` and `url` in the settings say. `web/API.md` says so; the UI does not show it.
- `dnsUpstream` may be the container's own address or its gateway. The first loops every direct-routed query back into the forwarder; the second does the same when the router forwards DNS to the container, but is a valid upstream when it does not, so neither is refused (the config check cannot see the container's addresses). The UI gives no warning. Reported in round 20.
- A proxy server that sends its data in 1-byte WebSocket frames or VMess chunks makes each a separate write and packet towards the LAN device: CPU and airtime, no memory. gRPC joins small pieces already. Reported in round 20, not changed.
- A relay direction waits for data with a 2 KiB buffer, but with the 16 KiB one when the last read before the wait was at least three quarters of it (or exactly 2 KiB). A proxy server, or a LAN device on its own connections, can arrange that, and an idle connection then costs as much as a busy one (93 to 117 KB over TLS with both directions; 256 of those are 23 to 29 MiB, which does not fit beside the clients). The strict rule (large buffer only after a full read) costs two reads and two writes per TLS record on every download; a read deadline would close the gap but the VMess reader keeps a read error for good. Round 21.
- After the TLS handshake a server can still leave up to 24 KiB of an unfinished handshake message in uTLS (a 32 KiB buffer) on each connection, down from 128 KiB. TLS 1.3 hides the record type, so the limit cannot tell it from data on its way. Round 21.
- A device (one IPv4 address or IPv6 /64) may hold 64 connections and all devices together 256. Idle relays end after 5 minutes, so a device that sits on 64 mostly idle connections has its new ones closed at once until some end, and a second router doing NAT behind this one counts as one device. Recycling the device's own longest-idle connection instead of refusing would need the last activity time on the inbound slot. With 256 or more active sources a new source is always refused (same class as the forged-source items above). Round 22.
- A gRPC server that allows few streams per connection, or retires its connections with GOAWAY, gets up to one TLS and HTTP/2 connection per tunnel: a replaced connection is kept until its last tunnel ends. Tunnels are bounded by the inbound cap, so that is at most 256 connections, each about the cost of a tunnel over WebSocket and TLS (not measured for gRPC with one stream per connection). Every lower bound tried in rounds 21 to 23 either refused new tunnels or cut other devices' long-lived ones, so there is none below the inbound cap.
- A gRPC stream is judged every 250 ms and counted as slow when data waited for its reader half that time and the reader took less than 256 KiB/s; 32 may be slow at once, and one connection may have 12 MiB unread over all its tunnels. A device that keeps replacing stalled streams can still hold what arrives before the first judgement: on many gRPC clients at once (a round-robin group, one connection each) about 3 MiB at 100 Mbit/s of WAN, beside the 32 slow streams that are allowed (9 to 14 MiB as measured in round 23, the test server included). On one gRPC client those streams share the 12 MiB with everyone: with 32 slow ones holding 8 MiB and the device's young ones the rest, other devices' downloads through that client drop to a fraction (2.3 against 12 MiB/s in the round-24 test) for as long as the device keeps at it, much as if it were using the bandwidth. When more than 32 are slow, the device with the most slow streams loses one: its oldest that has been slow for 2 s, or else its newest. When several devices hold the most, the one whose stream has just turned slow loses one; a device with many addresses can still arrange to be neither (each address with fewer slow streams than the target has), the same class as the item on the slow-stream cap above. A device with more than 32 parallel bulk streams over gRPC (a download manager with 40 segments) therefore loses segments during a wifi hiccup of half a second, which the 2 s window before round 24 did not do. DNS queries in flight (64) each use a proxied connection outside the 256, about 4 to 6 MiB at most. Rounds 23 and 24.
- Each open UI tab holds one event stream, and a browser allows six connections to one host over all tabs: with six tabs open in one browser, requests in every tab wait until one is closed. Sharing one stream between tabs, or closing it while a tab is hidden, would fix it. Round 23.
- Imported clients and the new clients of a subscription refresh are enabled and added to the group with id `default`, so they can carry the default rule's traffic at once, and a subscription whose links change between refreshes adds them again after the admin took them out. The UI and `web/API.md` say so now; whether it should only happen on a subscription's first fetch, or not for a group the admin has changed, is the owner's call. Round 24.
- **Open decision.** The `firefox` and `safari` fingerprints are Firefox 120 and Safari 16.0 in uTLS v1.8.2, the latest release; Xray 26.3.27 pins a newer uTLS commit (`v1.8.3-0.20260301010127`) where they are Firefox 148 and Safari 26.3. `random` resolves to `chrome` until then. Pinning that commit would bring them up to date; check the image size and whether its `decompressCert` still allocates 16 MiB first. Round 25.
- What the gRPC transport sends inside TLS matches neither Xray nor grpc-go: `:scheme` is `https` (grpc-go under Xray sends `http`), the pseudo-header order is x/net's, and the SETTINGS (`INITIAL_WINDOW_SIZE` 262144, `MAX_FRAME_SIZE` 16384, `MAX_HEADER_LIST_SIZE` 16384) and the 12 MiB connection window come from the memory limits of rounds 13 to 24. The server, or a CDN in front of it, can tell this client by them; a passive observer cannot under TLS. The WebSocket request has a Chrome User-Agent but none of the other headers Xray adds (`Sec-CH-UA`, `Sec-Fetch-*`, `Accept-Language`). Round 25.
- A client's health is what the probe says. A subscription server that relays the probe and drops or delays everything else stays "up" and, in a least-ping group, current: failed dials are not counted, no other member is tried for a failed connection, and group switches are not logged. It needs to be 20 ms or 15 % faster on two checks, or the fastest left when the current member fails one probe. The Groups page marks untrusted members; `web/API.md` says to keep `healthUrl` on https. Counting dial failures as failed checks would be the fix. A changed member list also resets a failover group's three-check failback rule. Round 25.
- DNS answers are cached per route, so an answer fetched through one member of a group is served to every device using that group for its TTL, at most an hour, also after the group has moved to another member. A hostile member can forge answers; proxied TLS and HTTP are sent by sniffed name, so it matters for what cannot be sniffed and for availability. Round 25.
- `POST /api/clients/:id/toggle` flips the flag, so a request sent twice undoes itself. Round 25.
- With an unset clock (the router after a power cut) TLS to the proxy servers and VMess fail until the time is set; only the health probe allows for it. Check on the device what clock RouterOS starts with. Round 25.
- Build: `make image` embeds whatever `web/dist` holds, or a placeholder, without failing; the extracted `.tools/upx` is checked only when downloaded; the Dockerfile copies the whole `web/dist`, not only the `.gz` files. Round 25.
- A client's `alpn` is kept, shown and exported but not sent: under a browser fingerprint (always, here) the hello offers the browser's own list, as in Xray. Only WebSocket (`http/1.1`) and TCP with exactly `http/1.1` differ. This is a setting that is not honoured without being refused, against the project's rule, because links with `alpn=h2` are common and refusing them would refuse working servers; the form and `web/API.md` say so. Round 26.
- Share links with raw Unicode host names are rejected; the punycode form works.
- Not supported and refused at import: VLESS encryption, Reality `pqv`, legacy VMess (`alterId` above 0).
